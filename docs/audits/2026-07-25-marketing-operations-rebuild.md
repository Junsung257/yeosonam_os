## 근본 원인

1. 운영 `ad_traffic_logs`에는 `gbraid`, `wbraid`가 없지만 추적 코드는 두 필드를 항상 INSERT payload에 포함했다.
2. 과거 `20260608153000_ad_os_paid_assisted_attribution.sql`은 저장소에 있으나 운영 마이그레이션 이력에 반영되지 않았다.
3. `/api/tracking`은 주요 DB 쓰기를 기다리지 않고 202를 반환했다.
4. `src/lib/db/ads.ts`는 Supabase 반환 오류를 확인하지 않았다.
5. 대시보드는 존재하지 않는 `ad_traffic_logs.count`를 조회하고, 클릭을 방문의 2%로 추정하며, 빈 퍼널을 최소 1건으로 표시했다.
6. 광고사 성과 스냅샷이 0건인데도 미수집과 실제 0을 구분하지 않았다.
7. 채널 점검이 47일 이상 오래됐지만 초안 준비 상태를 운영 준비처럼 해석할 여지가 있었다.

## 구현한 변경

- 주요 추적 쓰기와 세션 병합을 await하고 Supabase 오류를 실패로 처리.
- 주요 저장 실패는 503과 `accepted:false`, `retryable:true`로 응답.
- 선택적 카운터 실패는 주요 행의 중복 재시도를 막기 위해 202의 `warnings`로 분리.
- 운영 스키마 누락을 보정하는 idempotent 마이그레이션 추가.
- 광고사 노출·클릭·지출은 `ad_performance_snapshots`만 사용.
- 미수집 값은 숫자 0 대신 `not_collected`와 “수집 안 됨”으로 표시.
- 채널 상태는 최신 점검, 권한, 외부 계정, 캠페인, 실제 발행 가능 증거를 함께 평가.
- 기본 마케팅 화면을 쉬운 한국어의 우선 조치 → 핵심 수치 → 채널 → 고객 흐름 → 콘텐츠 → 캠페인 순서로 재구성.
- 소셜 설정 API에서 접근 토큰을 응답하지 않고, 화면에서 발행 허용과 계정 연결을 분리.
- 실제 실행 검사를 건너뛴 준비도 검사는 pass가 아니라 partial/blocked로 기록.

## 외부 기준 대조

- [Google Ads 자료 최신성 안내](https://support.google.com/google-ads/answer/2544985?hl=en)는 클릭·노출·비용도 즉시 확정되지 않으며 일반적으로 시간 단위로 갱신되고, 전환은 귀속 방식에 따라 더 늦게 바뀔 수 있다고 설명한다. 따라서 화면에 자료 갱신 시각을 표시하고 최근 수치를 확정값처럼 단정하지 않는다.
- [Supermetrics 자료 갱신 안내](https://docs.supermetrics.com/docs/about-data-source-refresh-frequency)는 소스 API의 지연이 자체 새로고침 주기보다 우선한다고 설명하며, [과거 기간 재수집 안내](https://docs.supermetrics.com/docs/about-refresh-settings-in-data-warehouse-transfers)는 광고·전환 자료를 귀속 기간만큼 다시 수집하는 설정을 제공한다. 따라서 후속 운영 단계에는 귀속 기간 재수집이 필요하다.
- [AgencyAnalytics 대시보드 안내](https://agencyanalytics.com/blog/agency-dashboard)는 여러 채널의 기본 수치를 한 화면에 모으되 역할별로 다른 상세 수준을 제공하는 방식을 강조한다. 따라서 기본 화면은 비전문 운영자용으로 단순화하고 Ad OS 상세는 접힌 전문가 도구로 남겼다.

## 운영 적용 전 남은 게이트

1. 새 마이그레이션을 운영 DB에 적용한다.
2. 배포 후 consent 있음/없음 유입 이벤트를 각각 보내 실제 행과 202 응답을 함께 확인한다.
3. Google/Naver/Meta 중 한 채널의 읽기 전용 성과 동기화를 실행해 `ad_performance_snapshots`를 생성한다.
4. 채널 점검을 새로 실행하고 최근 점검 시각이 갱신되는지 확인한다.
5. 실제 전환 1건에서 내부 저장과 외부 전달 결과를 별도로 확인한다.
6. 운영 브라우저에서 데스크톱·모바일·키보드 사용성을 확인한다.
